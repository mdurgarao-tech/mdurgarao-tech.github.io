Akamai CDN/WAF Migration Programme

Flagship case study

Production workLitehires Global

One production migration programme, covering Akamai to Cloudflare and Akamai to AWS CloudFront. I supported the security and traffic-path side of it. This is described at process level, without customer details.

Environment
Akamai CDN and Kona Site Defender as the source. Cloudflare and AWS CloudFront as the targets. DNS, TLS certificates (ACM on the AWS side) and the application origins.
My role
Network Security Analyst. I supported WAF policy mapping, DNS and TLS preparation, cutover, validation, troubleshooting and documentation.

Workflow

  1. Application discoveryIdentified the applications in scope.
  2. Application inventoryRecorded the inventory before any change was made.
  3. Staging / lower-environment validationValidated the target setup in a lower environment before production.
  4. WAF policy mappingMapped the Akamai security policy to the target platform.
  5. DNS / CNAME preparationPrepared the DNS and CNAME changes.
  6. TTL reductionLowered the DNS TTL ahead of the cutover so that a change, or a rollback, takes effect quickly.
  7. TLS / certificate validationValidated the certificates and TLS setup on the target.
  8. Production cutoverMoved traffic by DNS/CNAME change, with a rollback path to Akamai kept ready.
  9. CDN / WAF / origin validationChecked cache hit and miss behaviour, TLS versions, HTTP response codes and WAF events after go-live.
  10. HTTP 403 / 502 troubleshootingInvestigated 403 and 502 responses during the migration.
  11. Rollback validationRollback to Akamai was validated when it was required.
  12. Post-cutover monitoringKept watching response codes, WAF events and origin behaviour after the change.
  13. Migration documentationDocumented the migration findings and implementation details.

How did you validate the change?

After go-live I checked four things: cache hit and miss behaviour, TLS versions, HTTP response codes and WAF events.

How did you map WAF policies?

I took the existing Akamai security policy and mapped the required controls to the target platform, then validated the result in a lower environment before production.

How did you validate TLS and the origin?

For TLS, the certificates on the target and the TLS versions clients negotiate. For the origin, that the CDN could reach it and that cache and origin behaviour matched what the application needed.

How did you troubleshoot a 403?

Find which layer sent it, using response headers and CDN or WAF logs for the same time, URI and method. If the WAF blocked it, find the rule and the part of the request that triggered it. If the WAF allowed it, follow the request on to the load balancer and application.

How did you troubleshoot a 502?

I do not treat it as a WAF block first. I check whether the CDN can reach the origin: DNS for the origin, connectivity, the TLS handshake and origin health. If the origin answers with an error, the problem is behind the CDN.

How did you handle rollback?

The rollback path to Akamai was prepared before cutover, the TTL was already lowered, and rollback was validated when it was required.

Not included: the number of applications, traffic volumes, timelines and performance figures. I only state numbers I can defend. Process notes on GitHub.

WAF Security Operations & False-Positive Tuning

Project

Production workLitehires, Unizen, Deloitte USI

Day-to-day WAF operations across several platforms and employers. The platforms were Akamai Kona Site Defender, Imperva, AWS WAF, Cloudflare and Cloud Native (Azure) WAF.

Environment
Enterprise web applications behind a CDN and WAF, with WAF and Splunk logs and ServiceNow for requests, incidents and changes.
My role
WAF onboarding, rule and policy configuration, event and attack-signature analysis, false-positive handling, and coordination with application teams.

What the work covers

  • Application onboarding and security-policy configuration.
  • Event and attack-signature analysis, including SQL injection, XSS, file inclusion and command injection attempts.
  • Identifying false positives and handling them with controlled exceptions.
  • Working with application teams to understand legitimate traffic before changing a rule.
  • Reading HTTP headers, methods and response codes during an investigation.
  • Tracing a request from the CDN through the WAF to the origin.
  • Validating the result in production after a change.

How did you analyse WAF events?

Start from the event and the rule that fired. Then match the source, URI, HTTP method and timestamp, look at the part of the request that triggered the rule, and decide whether it is an attack or normal application behaviour.

How did you handle false positives?

Confirm with the application team that the request is legitimate, then add a narrow exception scoped to that application, URI or parameter. I do not disable a whole rule. Then retest and watch the same rule's events.

How did you troubleshoot a 403 or 502 in this work?

The same method as in the migration case study: find which layer produced the response, then follow the request through CDN, WAF and origin before changing anything. Method notes on GitHub.

FireMon Firewall Rule Optimization

Project

Production workLitehires Global

Rule-base review and cleanup across 50+ firewalls, with 2,000+ rules optimized using FireMon.

Environment
Palo Alto, Fortinet, Check Point and Cisco ASA firewalls, with FireMon for rule analysis.
My role
Network Security Analyst. I reviewed rules, analysed shadowed and unused rules, validated with business owners, and supported the cleanup and the checks after each change.

What I looked at

  • Shadowed rules: rules that can never match because an earlier rule already covers the same traffic.
  • Unused rules: rules with no matches over the review period.
  • Business-owner validation: checking with the owner before changing or removing a rule.
  • Change validation and traffic-flow troubleshooting: confirming the intended traffic still works after a change, and tracing it when it does not.

How did FireMon help?

It analysed the rule bases and pointed to shadowed and unused rules, so the review started from evidence.

Why check with business owners?

Hit counts only show the past. A rule that looks unused may serve a process that runs rarely. Confirming with the owner is what makes a cleanup safe.

How did you validate firewall rule changes?

By checking that the intended traffic still passed after the change, and tracing the traffic flow when something did not work.

The only figures here are 50+ firewalls and 2,000+ rules. I have not stated an optimization percentage. Process notes on GitHub.
